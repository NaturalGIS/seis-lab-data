# User guide

SeisLabData is a web application for cataloguing marine survey data. It keeps a catalogue of
projects, of the survey missions carried out within each project and of the survey-related records
that describe the data files produced by each mission. The data files remain in the archive file
system; the catalogue stores their metadata, their location in the archive and derived previews.

Records can be created by hand or generated by a mission discovery, which scans a mission's
directory in the archive and creates a record for each file matching the configured path
patterns, extracting its spatial extent, temporal extent and other metadata from the file itself.

The catalogue is published through the web interface and through a STAC API, available at the
`/stac` path, which exposes published items only.

The user interface is available in Portuguese and in English. The language is selected in the
language menu of the top bar. Data entered by users, such as names and descriptions, is not
translated.


## Concepts

### Projects, missions, records, assets

The catalogue is organised as a hierarchy:

```
Project
  └── Survey mission (many per project)
        └── Survey-related record (many per mission)
              └── Asset (many per record)
```

- **Project** - The top-level grouping, typically corresponding to a contract or a study. A
  project holds survey missions.
- **Survey mission** - A data collection campaign within a project. A mission is linked to a
  directory of the archive, its relative path, and holds survey-related records.
- **Survey-related record** - The description of a dataset produced by a mission, for example a
  processed bathymetry grid or a seismic line. A record is classified by a dataset category and a
  workflow stage and holds one or more assets.
- **Asset** - A file belonging to a record. Data assets refer to files in the archive. Derived
  assets, such as previews, are generated by the application.

Projects, missions and records share a set of common properties:

| Property | Description |
|----------|-------------|
| Name | Identifies the item. Up to 100 characters. |
| Description | Short description of the item. Up to 500 characters. |
| Spatial extent | Bounding box of the item, in WGS 84 longitude and latitude. |
| Temporal extent | Begin and end dates of the item. |
| Links | Up to 5 links to external resources, each with a URL, a media type, a relation and a description. |
| Status | Current state of the item, described in [Resource state](#resource-state). |

Records can additionally be related to other records, as described in
[Relate records with each other](#relate-records-with-each-other).

### Resource state

Each project, mission and record has a status. Stable states are those in which an item can be
modified by users. Transitory states are held while a background task is working on the item.

**Stable states:**

- **draft** - The item is visible to authenticated users only.
- **published** - The item is visible to all users, including anonymous ones.

Items are not published or unpublished by hand. After each creation or update, the item is
validated and its status is set as follows:

- A project is published if it is valid, and set to draft otherwise.
- A survey mission is published if it is valid and its project is published.
- A survey-related record is published if it is valid and its mission is published.

Changes propagate to the items below:

- When a valid project is updated, its valid draft missions are published, followed by their
  valid draft records.
- When a project becomes invalid, its missions and their records are set to draft.
- When a mission is updated, its valid draft records are published if the mission is published,
  and set to draft otherwise.

An item is valid when:

- its name has between 5 and 100 characters;
- its description has up to 500 characters;
- every link has an `http` or `https` URL;
- it has a spatial extent with a non-zero area;
- for records, a dataset category and a workflow stage are set.

The temporal extent is optional. For draft items, the information panel of the detail page shows
whether the item is valid and lists the validation errors.

**Transitory states:**

| State | Applies to | Held while |
|-------|------------|------------|
| under validation | projects, missions, records | the item is validated after a creation or update |
| under discovery | missions | a mission discovery is running |
| cancelling discovery | missions | a cancellation of a running discovery has been requested and is being processed |
| under derivation | records | newly generated previews are being stored |
| under export | records | the record is being exported to GeoNode |

While an item is in a transitory state it cannot be updated or deleted. In addition:

- While a mission is under discovery or cancelling discovery, its records cannot be created,
  updated or deleted, bulk updates skip them, and no other discovery of the mission can be
  started.
- A project cannot be deleted while any of its missions or records is in a transitory state.
  A mission cannot be deleted while any of its records is in a transitory state.

At the end of a task the item returns to the status it had before the task started.

### Mission discovery

A mission discovery scans the mission's directory in the archive and creates one survey-related
record for each file that matches an asset discovery configuration. Each record holds one data
asset pointing to its file. The record's spatial extent and temporal extent are extracted from
the file's metadata, and its dataset category and workflow stage are taken from the
configuration.

Discovery is configured through asset discovery configurations, described in
[Asset discovery configurations](#asset-discovery-configurations). It is started from the
mission's detail page, as described in
[Discovering survey mission contents](#discovering-survey-mission-contents).


## Users and permissions

**Anonymous users** can browse and search published projects, missions and records, download the
assets of published records and use the STAC API. Unpublished items are not shown to them.

**Authenticated users** can see all items, including drafts. What they can modify depends on their
roles:

| Role | Permissions |
|------|-------------|
| none | Read access to all items, including drafts. |
| `catalog-editor` | Full access: create, update and delete projects, missions, records and settings resources, run and cancel discoveries, bulk-update records and export records to GeoNode. |
| `system-admin` | The same permissions as `catalog-editor`, plus access to the Authentik administration interface through the user menu. |

Permissions do not depend on who created an item: users with the `catalog-editor` or
`system-admin` role can modify any item.

User accounts and roles are managed in [Authentik](https://goauthentik.io/), the authentication
service used by the platform. Users log in through the **Login** link of the top bar, which leads
to the Authentik login page. The platform does not allow self-registration: accounts are created
by a system administrator in Authentik.

The user menu of the top bar shows the username, e-mail, identifier and roles of the logged-in
user.


## Working with projects

A project groups the survey missions of a contract or study. Its properties are the common
properties listed in [Projects, missions, records, assets](#projects-missions-records-assets).

The project's detail page shows its properties, a map with its spatial extent, a summary of its
records by dataset category and by workflow stage, and the list of its survey missions. Selecting
a category or stage in the summary opens the list of the project's records with that category or
stage.

### Searching for projects

The project listing is available at `/projects/`. Results are ordered by the end of their
temporal extent, most recent first, then by the begin of their temporal extent and by name, and
are shown in pages of 20 items.

The following filters are available:

| Filter | Description |
|--------|-------------|
| search projects | Projects whose name contains the given text, ignoring case. |
| status | Projects in the selected status, such as draft, published or under validation. Available to authenticated users. |
| Temporal extent begin, end | Projects whose temporal extent overlaps the given dates. A temporal extent without a begin or an end is taken as open on that side, and projects without a temporal extent are also included. |
| filter by map area | When switched on, projects whose spatial extent intersects the visible area of the map. Projects without a spatial extent are also included. The results are updated when the map is moved. |

The status, temporal and map filters are shown with the **toggle advanced search controls** button.
The filters are kept in the page's address, so reloading or sharing it keeps them. Selecting a project's extent on the map opens the project's detail page.

### Create a new project

Users with the `catalog-editor` or `system-admin` role are able to create a project with the
**Add new project** button of the project listing. The form has the following fields:

| Field | Description |
|-------|-------------|
| Name | Required. Identifies the project and must be unique among all projects. Up to 100 characters; a valid project requires at least 5. |
| Description | Optional. Summary of the project, up to 500 characters. |
| Spatial extent | Minimum and maximum longitude and latitude of the area covered by the project, in decimal degrees, entered as numbers or drawn as a rectangle on the map. A valid project requires an extent with a non-zero area. |
| Temporal extent begin, end | Optional. Dates of the beginning and end of the project. |
| Links | Optional. Up to 5 links to external resources related to the project, added with **Add another link**. Each link has a URL, which must use `http` or `https`, a media type, a relation and a description of up to 500 characters. |

The project is created with the **Create project** button. It is then validated and, if valid,
published. A thumbnail showing its spatial extent over a base map is generated when the project
is created with a spatial extent and whenever its spatial extent changes.

### Update project details

The **edit project** button of the project's detail page opens a form with the same fields as the
creation form. Saving the form validates the project again and updates the status of the project
and of its missions and records, as described in [Resource state](#resource-state).

### Delete a project

The **delete project** button of the project's detail page deletes the project after a
confirmation. Deleting a project also deletes its survey missions, their survey-related records
and the records' assets. Files in the archive are not modified. The button is disabled while
the project, or any of its missions or records, is in a transitory state; the info section then
says so.


## Working with survey missions

A survey mission is a data collection campaign within a project. In addition to the common
properties listed in [Projects, missions, records, assets](#projects-missions-records-assets), a
mission has the following properties:

| Property | Description |
|----------|-------------|
| Relative path | Path of the mission's directory in the archive, relative to the archive root. Discovery scans this directory, and the paths of the mission's assets are relative to it. |
| Implicit CRS | EPSG code of the coordinate reference system assumed for discovered files that do not declare one. |

The mission's detail page shows its properties, a map with its spatial extent, a summary of its
records by dataset category and by workflow stage, and the list of its records.

### Searching for survey missions

Survey missions are listed in two places:

- The survey mission listing, at `/survey-missions/`, lists the missions of all projects. It
  offers the **search survey missions** and **status** filters and the temporal and map filters, as described in
  [Searching for projects](#searching-for-projects).
- The project's detail page lists the project's missions, with a name search and the **status**
  filter.

The home page shows the three most recent missions.

### Create a new survey mission

A mission is created with the **add new survey mission** button of its project's detail page. The
form has the following fields:

| Field | Description |
|-------|-------------|
| Name | Required. Identifies the mission and must be unique among the missions of the project. Up to 100 characters; a valid mission requires at least 5. |
| Description | Optional. Summary of the mission, up to 500 characters. |
| Relative path | Optional. Path of the mission's directory in the archive, relative to the archive root directory. Required for running a discovery. |
| Implicit CRS | Required. EPSG code assumed for discovered files that do not declare a coordinate reference system. Defaults to 32629 (WGS 84 / UTM zone 29N). Typing a code or a CRS name shows matching suggestions. The code must identify a projected or geographic CRS. |
| Spatial extent | Minimum and maximum longitude and latitude of the area covered by the mission, in decimal degrees, entered as numbers or drawn as a rectangle on the map. A valid mission requires an extent with a non-zero area. |
| Temporal extent begin, end | Optional. Dates of the beginning and end of the data collection campaign. |
| Links | Optional. Up to 5 links to external resources related to the mission. Each link has a URL, which must use `http` or `https`, a media type, a relation and a description of up to 500 characters. |

The implicit CRS is used for files whose format cannot declare a coordinate reference system,
such as XYZ and some SEG-Y files. Missions outside UTM zone 29N, for example around Madeira or
the Azores, require the corresponding CRS to be set. With a geographic implicit CRS, coordinates
expressed in metres fall outside the valid longitude and latitude ranges, and the records of such
files are created without a spatial extent.

### Update survey mission details

The **edit survey mission** button of the mission's detail page opens a form with the same fields
as the creation form. The button is disabled while the mission is in a transitory state.

### Discovering survey mission contents

The **discover records...** button of the mission's detail page starts a discovery after a
confirmation. The button is disabled when the mission has no relative path or is in a
transitory state. Discovery requires:

- the `catalog-editor` or `system-admin` role;
- a mission in the draft or published state;
- a relative path that names a directory inside the archive, other than the archive root.

While the discovery runs:

- the mission is under discovery, and its records cannot be created, updated or deleted;
- the mission's status, in the info panel, shows a progress bar. Progress is measured in
  sections: the directories of the mission named by the literal start of the asset discovery
  configurations' path patterns (e.g. `s06-mbes/s02-raw-data`), which discovery goes through one
  after the other. The section being discovered is shown below the bar, with its middle
  directories left out when its path is long; hovering it shows the full path. Sections differ in
  size, so the bar moves unevenly: it may stay on a large section for a long time. The bar is
  animated while the discovery runs. It is full and grey until the sections are known, which is also how it
  shows on a page opened during a discovery, for a few seconds;
- below the bar, the number of files found, the number of records created and, when applicable,
  the number of files that could not be processed and the names of asset discovery
  configurations with an invalid path pattern;
- the list of the mission's records is refreshed at each progress update.

A notification is shown when the discovery starts and when it ends, is cancelled or fails.

Discovery creates one record for each file that matches an asset discovery configuration and is
not yet referenced by a record of the mission. The record is named after the file, takes its
dataset category and workflow stage from the matching configuration, and holds one data asset
referring to the file. Its spatial extent and temporal extent are extracted from the file's
metadata, and the other extracted metadata is shown on the record's detail page. For files whose
metadata does not identify a coordinate reference system, the mission's implicit CRS is used.

Records created by discovery are validated as they are created. When the discovery ends, the valid
records are published if the mission is published, and the other records remain in draft status.
This applies also when the discovery is cancelled, fails or exceeds its time limit, to the records
created until then.

For some formats, the metadata is extracted from samples of the file rather than from the whole
file:

- KMALL files are read in 16 windows of 256 KB, at both ends of the file and evenly spaced in
  between.
- XYZ files whose points do not form a regular grid, such as accepted soundings, are read in 128
  windows of 64 KB, and their point count is estimated.

The resulting extents are approximations. See [Supported formats](https://seis-lab-data.ipma.pt/docs/supported-formats/) for the
formats from which metadata is extracted.

Previews are generated for the created records whose configuration has
**Generate previews** enabled, while the discovery runs. At the end of the discovery, previews
are also requested for the mission's older records that do not have them.

**Running a discovery again** skips the files that are already referenced by a record of the
mission. If such a record has no spatial extent and the mission's implicit CRS is projected, its
spatial extent and temporal extent are extracted again, and so is the metadata shown on its
detail page. This allows correcting the records of a mission that was discovered with an
unsuitable implicit CRS: correct the implicit CRS, then run the discovery again.

**Cancelling a discovery:** the **cancel discovery...** button stops a running discovery after a
confirmation. The mission is set to cancelling discovery until the discovery stops. The records
created until then are kept. If the discovery process no longer runs, for example after a
server restart, requesting the cancellation again restores the mission after 10 minutes without
progress.

If not done by then, a discovery stops after 24 hours. The records created until then are kept, and running the
discovery again continues with the remaining files.

### Delete a survey mission

The **delete survey mission** button of the mission's detail page deletes the mission after a
confirmation. Deleting a mission also deletes its survey-related records and their assets. Files
in the archive are not modified. The button is disabled while the mission, or any of its
records, is in a transitory state; the info section then says so.


## Working with survey-related records

A survey-related record describes a dataset produced by a survey mission. In addition to the
common properties listed in [Projects, missions, records, assets](#projects-missions-records-assets),
a record has the following properties:

| Property | Description |
|----------|-------------|
| Dataset category | Classification of the dataset, as described in [Dataset categories](#dataset-categories). |
| Workflow stage | Processing stage of the dataset, as described in [Workflow stages](#workflow-stages). |
| Assets | Files belonging to the record, as described in [Working with record assets](#working-with-record-assets). |
| Related records | Relationships to other records, as described in [Relate records with each other](#relate-records-with-each-other). |

The record's detail page shows its properties, a map with its spatial extent and, when
available, its preview, its relationships to other records, and its data assets with a download
button for each. The properties also include the metadata extracted from the record's data file,
such as its format, CRS and size.

### Searching for survey-related records

Survey-related records are listed in two places:

- The record listing, at `/survey-related-records/`, lists the records of all missions.
- The mission's detail page lists the mission's records.

Both listings offer the following filters:

| Filter | Description |
|--------|-------------|
| search survey-related records | Records whose name contains the given text, ignoring case. |
| status | Records in the selected status, such as draft, published or under export. Available to authenticated users. |
| dataset category | Records with the selected dataset category. |
| workflow stage | Records with the selected workflow stage. |
| media type | Records with an asset of the given media type. |
| Temporal extent begin, end | As described in [Searching for projects](#searching-for-projects). |
| Path | Records with an asset whose relative path contains the given text. |

The record listing additionally offers a **project** and a **mission** filter, and the map
filter described in [Searching for projects](#searching-for-projects).

The record lists offer the following actions:

- **select all on this page** and **Select all records that match your search** select
  records for a bulk update; **clear selection** clears the selection.
- **bulk update** opens the bulk update form for the selected records. It is available on the
  mission's detail page, to users with the `catalog-editor` or `system-admin` role, while the
  mission is not under discovery.
- **download links** produces a text file with the download links of the assets of the listed
  published records, for use with a download manager such as `aria2c`.
- **regular layout** and **compact layout** switch between the two list layouts.

### Create a new survey-related record

In addition to mission discovery, records can be created by hand, with the
**add new survey-related record** button of the mission's detail page. The button is disabled
while the mission is under discovery. The form has the following fields:

| Field | Description |
|-------|-------------|
| Name | Required. Identifies the record and must be unique among the records of the mission. Up to 100 characters; a valid record requires at least 5. |
| Description | Optional. Summary of the dataset described by the record, up to 500 characters. |
| Dataset category | Required. Classifies the record by the type of data it describes. The list holds the categories defined in [Dataset categories](#dataset-categories). |
| Workflow stage | Required. Indicates the processing stage of the data, such as raw or processed. The list holds the stages defined in [Workflow stages](#workflow-stages). |
| Spatial extent | Minimum and maximum longitude and latitude of the data, in decimal degrees, entered as numbers or drawn as a rectangle on the map. A valid record requires an extent with a non-zero area. Replaced by the extent extracted from the record's data file, when one is extracted. |
| Temporal extent begin, end | Optional. Dates of the first and last acquisition of the data. Replaced by the dates extracted from the record's data file, when both are extracted. |
| Links | Optional. Up to 5 links to external resources related to the record. Each link has a URL, which must use `http` or `https`, a media type, a relation and a description of up to 500 characters. |
| Assets | Optional. Up to 20 files belonging to the record, as described in [Working with record assets](#working-with-record-assets). |
| Related records | Optional. Up to 5 relationships with other records, as described in [Relate records with each other](#relate-records-with-each-other). |

When the record is created, metadata is extracted from the file of the first data asset with a
relative path. The extracted spatial extent and temporal extent replace those entered in the
form; values that cannot be extracted from the file are kept as entered. The other extracted
metadata is shown on the record's detail page. Previews are then generated as for discovered
records, according to the asset discovery configuration matching the asset's path.

### Update survey-related record details

The **edit** button of the record's detail page opens a form with the same fields as the
creation form. The form lists the record's data assets only. The button is disabled while the
record is in a transitory state or its mission is under discovery.

When the set of data asset paths changes, metadata is extracted again from the first data asset,
as on creation, and the record's previews are generated again. The other extracted metadata is
replaced by that of the new extraction, or removed when nothing can be extracted. Updates that do
not change the data asset paths keep the values entered in the form.

**Bulk update:** the **bulk update** action of the mission's record list updates the selected
records at once. The form shows the number of records to update. Each of the following groups of
fields is applied only when its checkbox is selected:

- **update dataset category**
- **update workflow stage**
- **update bounding box**
- **update temporal extent**
- **update related records**, which replaces the existing relationships of the records

Records in a transitory state are not updated. A bulk update does not validate the records nor
change their status.

### Delete a survey-related record

The **delete...** button of the record's detail page deletes the record after a confirmation.
Deleting a record also deletes its assets and its relationships to other records. Files in the
archive are not modified. The button is disabled while the record is in a transitory state or
its mission is under discovery.

### Relate records with each other

A record can be related to up to five other records, of any mission or project. Each
relationship is entered in the **related records** section of the record's form, with the
following fields:

| Field | Description |
|-------|-------------|
| Related record | The related record, selected among the suggestions shown while typing its name. |
| Relationship | Required. Name of the relationship, up to 50 characters, for example `derived from`. |

Relationship names are free text. The record's detail page lists the records it is related to,
under **related to**, and the records that are related to it, under **subject to**.

### Export a record to GeoNode

The **export to GeoNode...** button of a record's detail page uploads the record's data to GeoNode,
after a confirmation. The button is shown to users with the `catalog-editor` or `system-admin` role,
for published records with a data asset in one of the formats `.tif`, `.tiff`, `.gpkg`, `.geojson` or `.shp` - those
are the formats supported by GeoNode. The record is under export while the upload runs. Exporting a record again
replaces the previous export. The record's detail page shows the link to the GeoNode resource and the date of the export.


## Working with record assets

An asset is a file belonging to a survey-related record. There are two kinds of assets:

- **Data assets** refer to files in the archive. A record usually has one data asset holding
  its main data, and may hold others, for example auxiliary files of the same dataset.
- **Derived assets** are generated by the application from the data assets. A preview image is
  generated for each data asset in a supported format, and is used as the record's thumbnail in
  listings and shown over the map of the record's detail page. While a preview is being
  generated, authenticated users see a spinner over the record's thumbnail in the record
  listings.

Assets are managed in the **assets** section of the record's form. Each data asset has the
following fields:

| Field | Description |
|-------|-------------|
| Name | Required. Identifies the asset and must be unique among the assets of the record. Up to 100 characters. |
| Description | Optional. Summary of the file's content, up to 500 characters. |
| Media type | Optional. Media type of the file, used to identify its format, for example `image/tiff`. When empty, it is derived from the file extension, as `application/prs.ipma.<extension>`. |
| Relative path | Path of the file in the archive, relative to the mission's directory, for example `s06-mbes/s05-processed-data/grid.tif`. Must be unique among the assets of the mission. The metadata of the record is extracted from the file of its first data asset with a relative path. |
| Links | Optional. Up to 5 links to external resources related to the asset. Each link has a URL, which must use `http` or `https`, a media type, a relation and a description of up to 500 characters. |

Derived assets are not shown in the form and cannot be edited. They are replaced when the
record's data asset paths change.

The data assets of a record can be downloaded from its detail page by users who can see the
record. Shapefiles are downloaded as a zip file holding the `.shp` file and its sidecar files.


## Settings and auxiliary resources

Settings resources are managed from the **Settings** menu of the top bar, shown to authenticated
users. Only users with the `catalog-editor` or `system-admin` role can create, update or delete
them. Each list offers a search by name, and an **edit** and a **delete** action for each entry.
Deleting an entry requires a confirmation.

### Dataset categories

Dataset categories classify survey-related records by the kind of data they hold, for example
bathymetry or seismic data. Each record has a dataset category, which can be used to filter
records in the record listings. Dataset categories are managed at `/dataset-categories/`.

#### Create a new dataset category

The **Add new dataset category** button opens a form with a single **Name** field. Names must be
unique.

#### Update dataset category details

The **edit** action of a category's entry opens a form with its **Name** field.

#### Delete a dataset category

The **delete** action of a category's entry deletes the category. The records of a deleted
category are kept, without a dataset category, and are shown as **unknown category**. A record
without a dataset category fails validation until a category is set again.

### Workflow stages

Workflow stages classify survey-related records by the processing stage of their data, for
example raw data or processed data. Each record has a workflow stage, which can be used to
filter records in the record listings. Workflow stages are managed at `/workflow-stages/`.

#### Create a new workflow stage

The **Add new workflow stage** button opens a form with a single **Name** field. Names must be
unique.

#### Update workflow stage details

The **edit** action of a stage's entry opens a form with its **Name** field.

#### Delete a workflow stage

The **delete** action of a stage's entry deletes the stage. The records of a deleted stage
are kept, without a workflow stage, and are shown as **unknown stage**. A record without a
workflow stage fails validation until a stage is set again.

### Asset discovery configurations

Asset discovery configurations define which files of a mission's directory are turned into
records by a mission discovery, and with which dataset category and workflow stage. They are
managed at `/asset-discovery-configurations/`.

#### Create a new asset discovery configuration

The **new asset discovery configuration** form has the following fields:

| Field | Description |
|-------|-------------|
| Name | Required. Identifies the configuration. Must be unique. |
| Relative path regular expression | Required. Path pattern of the files matched by the configuration, as described below. |
| Media type | Required. Media type of the matched files. |
| Dataset category | Dataset category of the records created for the matched files. |
| Workflow stage | Workflow stage of the records created for the matched files. |
| Generate previews | Whether previews are generated for the assets matched by the configuration. |

The relative path regular expression is a path relative to the mission's directory, whose
segments are separated by `/`:

- The leading segments without regular expression characters form a literal prefix. Discovery
  only scans the directories below this prefix.
- Each remaining segment is a regular expression matching a whole directory or file name. The
  last segment matches the file name.
- Any number of directories may lie before, between or after the directories matched by the
  regular expression segments.
- A pattern without regular expression segments matches only the path it names.

For example, the pattern `s06-mbes/s02-raw-data/.*\.kmall` matches every file with the `.kmall`
extension below the `s06-mbes/s02-raw-data` directory, at any depth.

A file is assigned to the first configuration, in alphabetical order of configuration name, whose
pattern matches its path. The same rule determines whether previews are generated for a data
asset, including the assets of records created by hand. A configuration whose pattern is not a
valid regular expression is skipped, and its name is reported in the discovery's summary.

#### Update asset discovery configuration details

The **edit** action of a configuration's entry opens a form with the same fields as the creation
form. Changes apply to the discoveries started afterwards; existing records are not modified.

#### Delete an asset discovery configuration

The **delete** action of a configuration's entry deletes the configuration. Records do not
keep a reference to the configuration that created them, so deleting a configuration does not modify
any record. Files matched only by a deleted configuration are not discovered by later
discoveries.
